# PowerProof — Firestore Schema

This schema is designed so the same structure works for ANY factory,
ANY industry (electronics, garment, ceramics, food, chemical) — only
the data inside changes, not the shape. This directly supports the
"Scalability & sustainability" rubric point.

---

## Collection: `factories/{factoryId}`

One document per factory (demo uses exactly one: `factory_demo_x`).

```
factories/{factoryId}
├── name: string                    e.g. "Factory X"
├── industry: string                e.g. "electronics_components" (generic, no country name)
├── timezone: string                e.g. "Asia/Dhaka"
├── peak_hours: array<int>          e.g. [6,7,8]  (hour indices in the working day)
├── normal_cap_kw: number
├── peak_cap_kw: number             may differ on a crisis day (see crisis_events)
├── created_at: timestamp
```

## Collection: `factories/{factoryId}/lines/{lineId}`

```
lines/{lineId}
├── name: string                    e.g. "Line_A"
├── power_kw: number                power draw when running
├── units_per_hour: number
├── status: string                  "idle" | "running" | "down"
```

## Collection: `factories/{factoryId}/orders/{orderId}`

```
orders/{orderId}
├── line_id: string                 reference to lines/{lineId}
├── units_needed: number
├── deadline_hour: number           hour index within the working day
├── material_ready_hour: number     hour at which required material is available
├── material_source: string         "confirmed_stock" | "extracted_from_email" | "manager_entered"
├── material_confidence: string     "high" | "uncertain"  (set by Gemini extraction, NEVER
│                                    treated as ground truth — see extraction_log below)
├── status: string                  "pending" | "in_progress" | "complete" | "at_risk"
```

## Collection: `factories/{factoryId}/tariff/{hourIndex}`

```
tariff/{hourIndex}
├── hour: number                    0-9 (working day hour index)
├── rate_usd_per_kwh: number
├── is_peak: boolean
```

## Collection: `factories/{factoryId}/crisis_events/{eventId}`

```
crisis_events/{eventId}
├── type: string                    "grid_restriction" | "supplier_delay" | "machine_down"
├── description: string             human-readable, e.g. "Peak-hour cap cut to 180kW"
├── raw_source: string              original text (simulated email/notice) — kept for audit
├── created_at: timestamp
├── resolved: boolean
```

## Collection: `factories/{factoryId}/extraction_log/{logId}`

Every time Gemini reads an unstructured input (email, PDF), the result
is logged here — separately from the orders collection — so the UI can
always show "this came from AI extraction, confidence X, verify before
trusting."

```
extraction_log/{logId}
├── source_text: string             the raw input Gemini read
├── extracted_fields: map           {material: "...", quantity: ..., delay_days: ...}
├── confidence_note: string         Gemini's own stated uncertainty, if any
├── cross_checked: boolean          whether a human has confirmed this
├── created_at: timestamp
```

## Collection: `factories/{factoryId}/plans/{planId}`

Each solver run produces 3 plan documents (Plan A / B / C) for a given
crisis_event. Plans are proposals until approved.

```
plans/{planId}
├── crisis_event_id: string
├── plan_label: string              "Plan A — Cost Saver" | "Plan B — Deadline Protector" |
│                                    "Plan C — Balanced Resilience"
├── schedule: map                   { line_id: [hour_indices_active] }
├── total_cost_usd: number          computed by OR-Tools, not Gemini
├── total_kwh: number
├── peak_cap_respected: boolean
├── deadline_risk: map              { order_id: "safe" | "at_risk" | "missed" }
├── idle_hours: map                 { line_id: hours }
├── assumptions: array<string>      human-readable list, generated by Gemini from solver output
├── explanation: string             Gemini's plain-language "why this plan" text
├── feasible: boolean               from the independent validator
├── status: string                  "proposed" | "approved" | "rejected" | "superseded"
├── approved_by: string             manager identifier (demo: a fixed name)
├── approved_at: timestamp | null
├── created_at: timestamp
```

## Collection: `factories/{factoryId}/dispatch/{dispatchId}`

Created only after a plan is approved. This feeds both the Line
Display and the per-worker confirmation tracking.

```
dispatch/{dispatchId}
├── plan_id: string
├── line_id: string
├── message_text: string            short instruction, e.g. "Line A starts at hour 3"
├── message_image_ref: string       path to a simple icon/card image
├── color_code: string              "green" | "orange" | "red" — drives Line Display color
├── created_at: timestamp
├── confirmations: map              { worker_id: {confirmed: bool, timestamp} }
```

The `confirmations` map is what powers the manager's "who has NOT
confirmed yet" view — the core accessibility-meets-operations metric.

## Collection: `factories/{factoryId}/issue_reports/{reportId}`

Created when a worker taps a picture-button on the Report Panel.

```
issue_reports/{reportId}
├── line_id: string
├── issue_type: string              "no_material" | "machine_down" | "need_help"
├── reported_at: timestamp
├── triggered_replan: boolean
├── resulting_plan_id: string | null
```

## Collection: `factories/{factoryId}/decision_log/{logId}`

Append-only audit trail. Every approval and every replan writes one
entry here. This is what proves "human stayed in control" for the
Technical Merit rubric point.

```
decision_log/{logId}
├── action: string                  "plan_approved" | "replan_triggered" | "issue_reported"
├── actor: string                   "manager" | "worker" | "system"
├── plan_id: string | null
├── reason: string
├── timestamp: timestamp
```

---

## Why this shape supports scalability (rubric point)

- Everything is nested under `factories/{factoryId}` — adding a second
  factory means adding a second document, not changing any code.
- `lines`, `orders`, `tariff` are industry-agnostic field names (no
  "sewing machine" or "kiln" baked in) — a garment factory, a ceramics
  plant, or an electronics assembler all fit the same shape.
- `extraction_log` and `decision_log` are append-only and separate from
  operational data, so audit/compliance features can be added later
  without restructuring anything.
